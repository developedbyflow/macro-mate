Regula de bază: ecranele citesc doar din telefon

Coada pleacă spre server

requestSync() pornește sincronizarea după 800 ms. Telefonul ei află de bifă

Telefonul ei ține minte cursorul: cel mai mare version primit până acum. La fiecare sincronizare cere doar ce e mai nou.

idnameversion
a1Cumpărături 1 oct.12
f9Cumpărături 4 oct.42

Cu since=41 vine doar rândul f9, iar cursorul ei devine 42. Cu 2.000 de alimente contează: fiecare telefon primește doar ce s-a schimbat. applyPull nu suprascrie rândurile care au încă modificări în coada telefonului.

Pull filtrează după cine cere: alimentele vin toate; rețetele, variantele, planurile, listele și cămara doar din bucătăria ei; jurnalul, planul zilei, greutatea și profilul doar ale ei. Răspunsul conține și kitchenId. Dacă diferă de cel ținut în Dexie, telefonul golește tabelele de bucătărie și cere tot de la since=0.

De ce e nevoie de lacăt

Fără lacăt, două cereri care ajung în același timp pot pierde un rând:

  1. Telefonul tău ia version 41, iar telefonul ei ia version 42.
  2. Cererea ei se termină prima: în bază există 42, dar încă nu există 41.
  3. Un telefon cere since=40, primește 42, iar cursorul lui devine 42.
  4. Cererea ta se termină: acum apare și 41.
  5. Telefonul cere de acum since=42. Rândul 41 nu-l mai primește niciodată.

pg_advisory_xact_lock lasă o singură scriere la un moment dat, iar numărul se ia după lacăt. Așa 41 se salvează înainte ca altcineva să poată lua 42. Pentru doi oameni lacătul nu se simte: o scriere durează câteva milisecunde.

Când amândoi modificați același lucru

Câștigă ultima salvare care ajunge la server, pe tot rândul. Ștergerea e definitivă: rândul primește deleted_at și rămâne în bază ca semn pentru celălalt telefon. Dacă ar dispărea pur și simplu, telefonul ei n-ar avea de unde afla.

Fiecare piesă din desen e un middleware: o funcție prin care trece fiecare cerere, în ordinea din Program.cs. Ordinea contează:

  1. UseForwardedHeaders e primul: Caddy scrie adresa telefonului în X-Forwarded-For, iar piesa o pune în Connection.RemoteIpAddress. Fără ea, toate cererile ar părea că vin de la Caddy și ar împărți aceeași limită. Un X-Forwarded-For trimis de telefon e înlocuit de Caddy.
  2. UseRequestLocalization alege limba, ca refuzul să vină în limba ta.
  3. UseAuthentication citește cookie-ul, ca limitatorul să știe contul, pentru politica ai.
  4. UseRateLimiter numără și decide.

Firewall-ul

ufw (uncomplicated firewall) alege pe ce porturi primește serverul conexiuni. Un port e numărul care spune cărui program îi e destinată o conexiune.

PortPentru ce
22 TCPSSH
80 TCPHTTP: verificarea Let's Encrypt și trimiterea spre HTTPS
443 TCPHTTPS: aplicația
443 UDPHTTP/3, pe care Caddy îl oferă singur

Întâi permiți 22, apoi pornești firewall-ul; invers, conexiunea SSH se taie.

sudo ufw allow 22/tcp && sudo ufw allow 80/tcp && sudo ufw allow 443/tcp && sudo ufw allow 443/udp && sudo ufw enable

Caută Proceed with operation (y|n)? → y, apoi Firewall is active and enabled on system startup.

sudo ufw status verbose

Caută Status: active, Default: deny (incoming) și ALLOW IN pentru 22/tcp, 80/tcp, 443/tcp, 443/udp.

Docker și ufw. Docker scrie reguli proprii pentru porturile publicate de containere, pe lângă ufw. Doar web publică porturi (80 și 443, deschise oricum); api și db n-au ports:, deci nu se ating din afară. Nu le adaugi ports:.

Firewall-ul OVH. În panoul OVH, la IP-ul serverului, există un firewall de rețea opțional (Edge Network Firewall), oprit implicit. Dacă îl pornești, lași și acolo TCP 22, 80, 443 și UDP 443; altfel certificatul nu se emite. Dacă te-ai blocat afară, intri cu consola KVM din panoul OVH.

  1. Pe resend.com îți faci cont.
  2. Domains → Add Domain → macromate.exemplu.com (regiunea din Europa, dacă te întreabă).
  3. În Namecheap, Advanced DNS: TXT-urile la Host Records; MX-ul la Mail Settings → Custom MX. La Host scrii partea dinaintea domeniului: resend._domainkey.macromate, send.macromate. Valorile le copiezi exact din Resend.
  4. În Resend: Verify DNS Records.
  5. API Keys → Create API Key, cu Sending access. Cheia (re_…) apare o dată; o pui în .env.

Caută starea Verified la domeniu. Dacă folosești redirecționarea de email Namecheap pe domeniul principal, Custom MX o oprește. Fără cheie Resend, emailul ajunge doar în logurile API-ului (Email to …).

Cămara

Cămara e lista de alimente pe care bucătăria le are de obicei acasă; a înlocuit favoritele. Un aliment nou intră direct în ea. La „Adaugă” e tabul Cămara (Recente, Cămara, Toate, Rețete), pagina Alimente o arată implicit, alternativele și DeepSeek o folosesc întâi. La trecerea pe modelul nou, favoritele au intrat în cămară.

Id-ul unui rând din cămară se calculează din bucătărie și aliment, la fel în telefon și pe server. SHA-256 e o funcție care face din orice text un număr lung, mereu același pentru același text; din el se iau primii 16 octeți.

TypeScript · lib/pantry.ts (fragment)

export async function pantryItemId(kitchenId: string, foodId: string) {
  const hash = new Uint8Array(await crypto.subtle.digest('SHA-256',
    new TextEncoder().encode(`${kitchenId}:${foodId}`)))
  const hex = Array.from(hash.slice(0, 16), (b) =>
    b.toString(16).padStart(2, '0')).join('')
  return `${hex.slice(0, 8)}-${hex.slice(8, 12)}-…`
}

  • Emailul: POST /api/auth/me/email verifică parola actuală (5 greșeli = blocare 5 minute) și adresa nouă, apoi trimite linkul pe adresa nouă și răspunde 202. Adresa se schimbă abia la /confirm-email, din link.
